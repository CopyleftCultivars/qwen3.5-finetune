## [Unreleased]

### Added
- Make the calibrated candidate-4 bundle the app's default model (#24): `ModelService._defaultQwen35ModelSlug` is now `qwen35-recipe-v5-cactus-cq4-hessian`; `configureQwen35Model`/`resetQwen35Model` and the `qwen35_model_slug` preference still work. Staging docs updated (README) including that the Cactus graph files (`components/`, `optimized_ir*.json`, `raw_ir*.json`) are architecture-only and were copied byte-identical from `qwen35-combined-cactus-cq4` for #67. Unit test pins the default slug.
- Recipe form tab: fill the trigger template, post the result as a chat reply, offer 'Continue chat?' (#20)
- Recipe form tab (#20): a separate `Recipe form` mode validates crop, candidate plant and area with the recipe tool's own public `resolveCrop`/`resolvePlant` (no model call), runs the deterministic calculation live to show computability or the tool's own error code/message, treats an optional location as a suggestion-ranking hint only, and posts the result as a chat-style reply with the full recipe card plus QUICK instructions. `Continue chat?` seeds a new session through `SessionStore.createSessionFromRecipe`. The form synthesizes the trained `<tool_call>` assistant turn and its QUICK instruction prompt is byte-identical to candidate 4 on all 42 exact-trigger development turns (14 cases × `issue_64_ckpt423_seed_{42,43,44}`); the existing chat parity remains 120/120, 80/80, 80/80 and 120/120. Report: `docs/issue-20-recipe-form-2026-10-21.md`.
- Per-session memory and session management UI (#21)
- Per-session chat memory and session management (#21): sessions are persisted locally in a versioned `chat_sessions_v1` SharedPreferences envelope (one message list per session, including recipe JSON), the last active session is restored on launch, and the drawer can create, switch, rename and delete sessions. The pre-session `chat_history` value is migrated once. Model history is built from the active session alone with #19's exact `buildSessionConversationHistory` rules, so prompt parity stays 120/120, 80/80, 80/80 and 120/120. `SessionStore.createSessionFromRecipe` seeds a new session with a user turn plus the assistant reply and recipe JSON for #20's "Continue chat?". The owner's `memory_service.dart` and its keyword `memlocal` dependency are merged unchanged and initialized, but recall is deliberately not injected into any prompt (that is #22). Report: `docs/issue-21-session-memory-2026-10-19.md`.
- Chat trigger prefix and the recipe tool in the app (#19)
- Port the bioaccumulator recipe tool into the app (#19): `natural_farming_chat/lib/services/recipe_tool_service.dart` reproduces the reference `recipe_tool_oracle.py` full `recipe-tool-result-v2` JSON and the compact `recipe_tool_served_view_v1`; `recipe_prompt.dart`/`farming_tools.dart` carry the runner's byte-identical `trigger_recipe_v1` system prompt and six-tool catalog (sha256 `9da18292…`, `216c4e45…`, `cd6e6b85…`); `tool_executor.dart` registers `bioaccumulator_recipe`; the fixed `Bioaccumulator recipe: <candidate plant> for my <crop>, <area> m2` phrase is shown as an in-chat hint. The model decides every chat turn: there is no trigger-prefix pre-router, all six tools in trained order are passed explicitly (no embedding routing), and history is the runner's full ordered conversation. On a recipe call, QUICK renders the runner's instruction turn (`[system, *history, user, assistant tool call, tool served view]`) with the same tools; DETAILED skips the instruction pass and renders the deterministic full recipe card. Both expose `Show full recipe`. Prompt parity is proven by exporting the app's real message lists and tools and rendering them with the runner's `cactus_qwen_prompt`: 120/120 decision prompts, 80/80 instruction prompts, 80/80 tool contexts and 120/120 histories exact across `issue_64_ckpt423_seed_{42,43,44}` (`docs/issue-19-prompt-parity-2026-10-19.json`). Golden fixtures generated by the reference MCP server cover all 56 development/validation v3 tool calls (never the test split); `pubspec.lock` is reverted to `main` (no new dependencies). The Qwen3.5 bundle slug is configurable while the current bundle stays the default. Report: `docs/issue-19-recipe-tool-app-2026-10-19.md`.
- Train candidate 5 on the app-rendered trigger-recipe corpus v6 (#66): `scripts/run_qwen35_targeted_v6_sft.sh` (branch `qwen3.5-finetune`, from `issue-64-recipe-v5-training`) runs the #64 LoRA recipe on `../bioaccumulator-benchmark-workspace/corpus/targeted_v6` with `--render app_chat_template` into the new `outputs/lora-adapter-qwen35-recipe-v6` (`checkpoint-{117,234,351,468}`, `final`; 468 steps, 6224.1 s, peak CUDA 5439.5 MiB; corpus eval loss 0.54741/0.53328/0.54077/0.55321). Merged `checkpoint-468` to `outputs/qwen35-recipe-v6-ckpt{117,234,351,468}-merged` and the chosen `outputs/qwen35-recipe-v6-merged`; the workspace selected it by the pre-registered worst-seed trigger rule on `scenarios/v3` development and ran the single validation gate (4/13 frozen `acceptance_gates_v2` metrics). No trainer source changed beyond the #63 mode; the combined/targeted-v2/v3/v4/v5 outputs and `natural_farming_chat` were untouched. The benchmark report is `docs/benchmark-results/trigger-recipe-candidate-5-v6-training-and-gate-2026-10-19.md`
- Train candidate 4 on the app-rendered trigger-recipe corpus v5 (#64): `scripts/run_qwen35_targeted_v5_sft.sh` (branch `issue-64-recipe-v5-training`, from `issue-63-app-chat-template-render`) runs the #59 LoRA recipe on `../bioaccumulator-benchmark-workspace/corpus/targeted_v5` with `--render app_chat_template` into the new `outputs/lora-adapter-qwen35-recipe-v5` (`checkpoint-{141,282,423,564}`, `final`; 564 steps, 8255.8 s, peak CUDA 5438.8 MiB; corpus eval loss 0.54944/0.53506/0.54587/0.56133). - Add the opt-in `--render app_chat_template` trainer mode (#63) so training can match the bytes the deployed app serves: `plain` (the default) is the historic `<|im_start|>{role}\n{content}<|im_end|>` rendering and is byte-for-byte unchanged, while `app_chat_template` renders the assistant generation boundary as `<|im_start|>assistant\n<think>\n\n</think>\n\n{content}<|im_end|>` exactly as Cactus `Tokenizer::format_qwen_style` (`vendor/cactus-sdk/cactus-engine/src/tokenizer.cpp:673-695`) and the Qwen3.5 `chat_template.jinja:147-154`, keeps earlier assistant history plain, never double-prefixes the retention rows that already carry a `<think>` block, and implies assistant-only masking so the empty think block is masked out of the loss (`scripts/train_qwen35_sft.py`; metrics record `render`, `app_chat_template` and the effective `assistant_only_loss`). Add `scripts/run_qwen35_targeted_v5_sft.sh` for the app-rendered corpus `../bioaccumulator-benchmark-workspace/corpus/targeted_v5`. `tests/test_app_chat_template_render.py` pins the renderer (single boundary vs history, no double prefix, unchanged default), the masking (with a deterministic character tokenizer so it runs without `transformers`), the CLI default and the byte-parity of sampled v5 rows against `scripts/run_hf_gpu_tool_benchmark.py::cactus_qwen_prompt(runner_default)` (#63)
- Add a local 210-item ladder scorer and a Cactus CQ conversion launcher for the combined adapter (#5, #6)
- Add flag-gated assistant-only loss masking and the targeted-v2 retrain script for the BF16 candidate; the trainer masks system/user/history tokens, honours the corpus `target_turn`/`messages[i].train` marker, and reports/verifies the masked-token fraction (#44)
